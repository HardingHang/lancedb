## 2. 测试范围

本报告评估 clustering-only，不显式创建 `BTREE`、`IVF`、全文索引或向量索引。查询收益来自聚簇布局、Lance fragment/page min-max 统计裁剪，以及顺序读局部性。

本报告中的 `2D`、`3D`、`4D` 表示参与聚簇和查询评估的标量维度数量：

- `2D`：使用 `lat`、`lng` 两列。
- `3D`：使用 `lat`、`lng`、`category_id` 三列。
- `4D`：使用 `lat`、`lng`、`category_id`、`timestamp` 四列。

数据分布如下：

| 分布 | 生成方式 | 测试含义 |
|:---|:---|:---|
| `uniform` | `lat ~ Uniform(-90, 90)`，`lng ~ Uniform(-180, 180)` | 无明显热点的基础场景，用于观察算法在均匀空间上的布局和裁剪能力。 |
| `gaussian` | `lat ~ Normal(0, 20)`，`lng ~ Normal(0, 40)` | 数据集中在中心区域，用于观察局部聚集分布下的裁剪效果和算法稳定性。 |
| `skewed` | `lat = Zipf(2.0) % 180 - 90`，`lng = Zipf(2.0) % 360 - 180` | 强热点倾斜场景，用于观察算法在热点块、非均匀密度下的退化风险。 |

算法组如下：

| 组 | 含义 |
|:---|:---|
| `A-R` | 不聚簇重写布局 |
| `B-H` | Hilbert 聚簇 |
| `B-Z` | ZOrder 聚簇，`bits = 16` |
| `B-X` | XMCK 默认参数 |
| `B-XM` | XMCK 中等块参数，`cu_size = 10000`, `cus_per_block = 1` |
| `B-XT` | XMCK 细块参数，`cu_size = 5000`, `cus_per_block = 1` |

其中 `A-R` 不是新的聚簇算法，而是把未聚簇数据重写成 20 个 fragment/data file，和各聚簇组的文件数量一致。它用于隔离“文件数量不同”本身带来的影响，是本文比较聚簇算法收益的 baseline。

查询场景如下：

| 场景 | 含义 |
|:---|:---|
| `S1_2D_Range` | `lat/lng` 二维范围查询 |
| `S2_1D_Range` | `lat` 一维范围查询 |
| `S3_Point_Query` | `lat/lng` 点查询 |
| `S4_Full_Scan` | 全表聚合扫描 |
| `S5_Mixed_Condition` | `lat range + lng point` 混合条件 |

## 4. 总体结论

- **聚簇对真实命中的范围查询收益明确。** `S1` 的二维选择率按每轴 `sqrt(selectivity)` 生成，`Rows` 接近标称选择率；`S3/S5` 使用真实存在的点值，避免把空结果误判为裁剪收益。

- **`S1/S2` 仍是判断算法收益的主依据。** 在 `uniform/gaussian` 的 `S1 10%` 中，最佳聚簇组相对 `A-R` 约 **6.7×–10.6×** 加速；`S2 10%` 中最佳组相对 `A-R` 约 **9.8×–11.5×**。`S1 50%` 收益会下降到约 **4.0×–6.7×**，符合高选择率下裁剪收益稀释的预期。

- **Hilbert/ZOrder 在二维范围主路径上仍最稳，XMCK 在单列范围和构建成本上更强。** `gaussian/2d S1` 中 `B-H/B-Z` 明显优于默认 `B-X`；`S2 10%` 中 `B-X/B-XM` 通常最快。XMCK 平均构建耗时约 **11.3s**，低于 Hilbert 的 **14.5s** 和 ZOrder 的 **13.5s**。

- **`skewed` 不是低选择率场景，而是热点场景。** 由于 Zipf 数据大量集中在 `lat=-89,lng=-179` 附近，`S1 0.1%/1%` 实际返回约 **37 万行**，`S2 0.1%/10%` 返回约 **61 万行**。聚簇仍有收益，但这是热点块压力测试，不能和 `uniform/gaussian` 的选择率直接类比。

- **`S5` 是“范围 + 点”的微命中场景。** 在 `uniform/gaussian` 下每次只返回 1 行，适合验证非空点值裁剪路径，不适合作为算法排序依据。

按查询场景看：

| 场景 | 结论 |
|:---|:---|
| `S1_2D_Range` | 主路径。`uniform/gaussian` 的行数接近标称选择率，`10%` 收益最清晰；`50%` 收益下降。 |
| `S2_1D_Range` | 单列范围查询收益非常稳定，`XMCK` 系列通常最好。 |
| `S3_Point_Query` | 使用真实存在的点值；连续分布下只返回 1 行，延迟差距小，不适合主排序。 |
| `S4_Full_Scan` | 用于确认全表扫描不会明显退化；聚簇不应期待降低读取量。 |
| `S5_Mixed_Condition` | 使用真实存在的点值；连续分布下主要是微命中点查，作为辅助观察。 |

本报告的主要算法判断以 `S1`、`S2`、构建成本和 XMCK 块统计为主。

## 7. XMCK 块统计分析

这张表用于解释 XMCK 为什么在不同分布下表现差异很大。XMCK 会把多维空间切成 block，再按 block 组织数据；block 越小且行数越均匀，范围查询越容易只读取少量局部数据。反过来，如果少数 block 吃掉大部分行，查询命中热点区域时仍会读取大量数据，聚簇裁剪效果会下降。

| `gaussian/2d` | `B-XM` | 10 | 83 | 1 | 365 | 124690 | 12048.2 |

主要结论：

- `uniform` 数据下 XMCK 表现符合预期：block 行数非常均匀。例如 `uniform/2d B-XT` 的 p50 约 `4452` 行、最大约 `4619` 行。
- `gaussian` 下默认 `B-X` 明显过粗：`gaussian/2d B-X` 最大 block 达 `803282` 行，远高于 p50 `30433` 行。这解释了默认 `B-X` 在 `gaussian/2d S1` 上明显慢于 `B-H/B-Z`。
- `B-XM/B-XT` 能缓解 gaussian 的热点问题：最大 block 从 `803282` 降到 `124690` 和 `65100`，但在 `S1` 上仍未完全追平 Hilbert/ZOrder。
- `skewed` 是 XMCK 参数中最难处理的分布：即使使用更细的 `B-XT`，最大 block 仍有 `923195` 行，说明等宽分桶无法有效拆散 Zipf 热点。

## 8. 结果解释

范围查询收益主要来自物理布局让 fragment/page min-max 更容易裁剪，并提升顺序读局部性。`Rows` 可以确认 `uniform/gaussian S1` 的返回行数接近标称选择率，因此 `S1` 适合作为主路径判断依据。

`Hilbert` 和 `ZOrder` 在二维范围查询上整体最稳，尤其是 `gaussian/2d` 这类中心聚集分布。`XMCK` 的优势更多体现在较低构建成本、单列范围查询，以及均匀高维场景下的可调参数。

`skewed` 的结果需要单独解释：它不是“0.1% 只返回 1000 行”的场景，而是热点数据导致同一个点/窗口命中大量重复坐标。这个结果说明等宽分桶和默认参数对极端热点不够鲁棒，后续需要考虑分位数分桶或自适应分桶。

## 9. 建议

建议保留现有默认算法策略，不把 `XMCK` 设为默认。理由是 `Hilbert/ZOrder` 在二维范围查询主路径上仍更稳，而 `XMCK` 对参数和数据分布更敏感。

建议对外暴露或文档推荐 `XMCK` 的定位为：需要更低聚簇构建成本、主要查询包含单列范围或高维聚簇列、并且用户愿意基于 workload 调整 `cu_size/cus_per_block` 的场景。

如果要给 XMCK 一个初始推荐参数，`B-XM` 或 `B-XT` 适合作为细块调优候选；但不建议把它固化为默认，因为 `skewed` 下热点块仍很大，且不同维度下最佳组会变化。

后续优先补充两类验证：`gaussian/skewed 3D/4D` 完整矩阵，以及针对 XMCK 的非等宽/分位数分桶可行性 benchmark。

## 10. 局限性

- 本报告不包含显式 `BTREE`、`IVF` 或全文索引，不能推导聚簇与索引组合后的收益。
- 本报告只覆盖正式主矩阵，未覆盖 `gaussian/skewed 3D/4D`。
- 结果来自 WSL2 单机环境，受 CPU、磁盘、OS page cache 和后台负载影响，不能直接等价于生产环境。
- per-group cold-cache 依赖 `sudo drop_caches`，只能控制 OS page cache，不能完全隔离所有硬件和运行时缓存。
- `S3` 和 `S5` 已保证真实命中，但在连续分布下返回行数很少，因此主要用于辅助观察，不作为主排序依据。
- `skewed` 数据的标称选择率和实际返回行数差异很大，解释时必须同时看 `Rows`。
- 本报告以 `p50` 作为主要排序依据，同时参考 `bytes_read`；如果目标是 tail latency SLA，需要单独提高 `p95/p99` 的权重。
