# LanceDB 多维聚簇性能测试最终报告

> **测试分支**: `feature/multi-dimensional-clustering`
> **测试时间**: 2026-04
> **主要测试规模**: Medium (1,000,000 行) / 128 维向量

---

## 1. 摘要

本报告基于可复现的 Python Benchmark 框架，量化评估了 LanceDB 多维聚簇（Multi-dimensional Clustering）在标量查询、向量融合查询及多种边界条件下的性能表现。

**核心发现**：
- **标量范围查询**是多维聚簇的**核心收益场景**。在聚簇键与过滤条件匹配的 2D 范围查询中，"聚簇 + BTREE 标量索引"组合在低 selectivity（0.1%）下可实现 **79 倍 IO 减少**；在 Gaussian 聚集分布下甚至达到 **552 倍 IO 减少**。
- **纯聚簇（无索引）**的收益主要来自**顺序局部性改善**（随机 IO → 顺序 IO），而非 fragment 跳过；在 10% selectivity 附近收益最大（5–6 倍提速）。
- **纯标量索引（无聚簇）**对无序数据的 2D 范围查询是**负优化**：索引减少了 `bytes_read`，但导致 IOPS 从 6 次暴涨到 2,262 次，随机 seek 开销吞噬了所有收益。
- **向量查询**中，IVF_PQ 索引本身是决定性因素（8–13 倍提速）。在 **1M 行 / Uniform 分布 / 128 partitions** 的测试条件下，聚簇未能在向量融合查询中显现出额外的正向收益，端到端 latency 较"仅向量索引"方案有 20–30% 的轻微增加。由于测试未覆盖 Gaussian/Skewed 分布的向量场景，且 `scan_stats_callback` 无法捕获索引文件 IO，该结论的适用范围存在明显限制。
- **维度越高，单维查询收益越低**：4D Hilbert 聚簇对 2D 范围查询的 IO 减少从 2D 的 79 倍稀释到 11 倍。
- **规模边界**：10M 行聚簇操作在当前测试环境触发 OOM（exit code 137），暴露出当前实现采用全内存排序的可扩展性瓶颈。

## 2. 测量指标定义

### 2.1 `latency_p50_ms` / `latency_p95_ms`

端到端查询延迟，从调用查询函数开始到返回完整结果为止。每个配置执行 3 次 warm-up + 20 次正式测试，取 P50（中位数）和 P95。

### 2.2 `bytes_read`

查询执行过程中，**底层数据扫描器实际从存储读取的原始字节总数**。该指标通过 `lance.Dataset.scanner(..., scan_stats_callback=...)` 采集。

**重要说明**：
- `bytes_read` **不包含** 索引文件（如 IVF_PQ 索引、BTREE 索引页）的读取量。
- 对于暴力扫描（A 组无索引），`bytes_read` 约等于被扫描列的数据总量。
- 对于使用 IVF_PQ 向量索引的查询（F/E 组），`bytes_read` 通常显示为 0，因为 Lance 的向量索引路径通过独立的索引文件获取候选向量，底层数据扫描器未被触发。

### 2.3 `iops`

`iops` 在本测试中指 **Lance `ScanScheduler` 向存储后端提交的数据读取 range 个数**。同样通过 `scan_stats_callback` 采集。

**统计口径与计算方法**：
1. 扫描器在读取一个 fragment 时，会收集所有需要读取的字节区间（如各列的 data page、footer 等）。
2. **合并**：若多个区间彼此紧邻（间距不超过 `block_size`），`FileScheduler` 会将它们合并为一个大的连续 range。
3. **切分**：若合并后的 range 超过 `max_iop_size`，会被切分为多个子 range。
4. **计数**：经过合并/切分后的最终 range 个数，即为 `iops`。

**关键推论**：
- 当数据在 fragment 内物理连续时（聚簇后），多个小读取会被合并为少数大读取 → **`iops` 显著下降**。
- 当数据随机分布时（未聚簇），读取区间分散无法合并 → **`iops` 暴涨**，即使 `bytes_read` 不高也会因大量随机 seek 而拖慢查询。

**未覆盖的部分**：
- **不是**操作系统层面的 `read()` 系统调用次数。
- **不统计** IVF_PQ 向量索引文件、BTREE 索引页的读取（这些走独立的索引读取路径，不经过数据集扫描器的 `ScanScheduler`）。

### 2.4 为什么 `bytes_read` 和 `iops` 需要一起看？

| 情况 | `bytes_read` | `iops` | 含义 |
|:---|---:|---:|:---|
| 顺序扫描大文件 | 高 | 低 | 高效利用带宽，主要成本在数据传输 |
| 随机读取分散小数据块 | 低 | 高 | 大量 seek 开销，存储请求调度成本占主导 |
| 纯索引查询（如 IVF_PQ） | 0 | 0 | 统计口径未覆盖索引文件读取，不代表零成本 |

本报告中多次出现的核心现象——**"bytes_read 下降但 iops 暴涨"**——正是负优化的典型信号。

## 3. 标量查询：聚簇的收益来源与机制拆解

### 3.1 范围查询（聚簇键命中）：D 组是最优解

在 2D 范围查询 `lat BETWEEN ... AND lng BETWEEN ...` 且 selectivity 为 0.1% 时：

| 组别 | Latency P50 | `bytes_read` | `iops` | 收益来源分析 |
|:---|---:|---:|---:|:---|
| A（无聚簇、无索引） | 6.99 ms | 28.0 MB | 6 | 基准线；metadata 已能跳过大部分 fragment |
| B（纯聚簇） | 7.11 ms | 20.3 MB | 89 | 顺序局部性改善，但 0.1% 时优化空间小 |
| C（纯索引） | 12.51 ms | 5.2 MB | **2,262** | 索引定位后随机读取 2,262 个不连续数据块 |
| **D（聚簇+索引）** | **3.72 ms** | **352 KB** | **84** | 索引精准定位 + 聚簇保证命中区域物理连续 |

**D 组的收益来源拆解**：
1. **聚簇的作用**：将 `lat/lng` 相近的行物理上压缩到连续的 fragment/page 中。当索引根据 `lat/lng` 范围过滤出候选行时，这些行不再"散落在上千个 fragment"，而是"集中在少量连续 page"。
2. **索引的作用**：在聚簇后的有序数据上，BTREE 能快速定位到边界，避免扫描边界外的连续数据。
3. **协同结果**：IOPS 从 C 组的 2,262 骤降到 84（随机→顺序），同时 `bytes_read` 从 5.2MB 再降到 352KB。

### 3.2 纯聚簇（B 组）的收益峰值在 10% selectivity

| Selectivity | B 组 Latency | A 组 Latency | Speedup | `bytes_read` 变化 | 收益来源 |
|:---|---:|---:|---:|:---|:---|
| 0.1% | 7.11 ms | 6.99 ms | 0.98x | 28M → 20M | A 组本身已很快，优化空间小 |
| 10.0% | 8.56 ms | 48.02 ms | **5.61x** | 38.6M → 24.7M | **随机 IO → 顺序 IO 的转换收益最大化** |
| 50.0% | 29.49 ms | 103.24 ms | 3.50x | 430M → 158M | 跳过+局部性双重收益 |

**10% 为什么是甜蜜点？**
- **0.1% 时**：A 组的 metadata 过滤已经很高效（只需读 28MB），B 组再优化空间有限。
- **10% 时**：A 组需要打开大量分散的 fragment（IOPS 高达 4,625），但每个 fragment 只读一小部分。B 组把这些分散的 fragment "压缩"成物理连续的几个大块，顺序一扫而过。虽然捎带读进了一些无关行（`bytes_read` 从 38.6M 降到 24.7M，降幅不大），但 IOPS 暴跌带来的调度收益占主导。
- **50% 时**：大部分 fragment 本来就要读，A 组的随机 seek 惩罚减小，所以 B 组的相对收益有所下降。

### 3.3 纯标量索引（C 组）为什么是负优化？

C 组在所有 2D 范围查询中都比 A 组慢（latency 0.5x–0.7x）。根因是**无序数据 + BTREE 索引 = 随机 IO 灾难**。

以 S1（0.1% selectivity）为例：
- C 组 `bytes_read` 确实比 A 组少 5 倍（28M → 5M）
- 但 **IOPS 从 6 次暴涨到 2,262 次**
- 在 Lance 的列式存储架构中，一次打开 fragment、读取 metadata、再读取匹配 page 的完整流程（即 1 次 IO）的延迟，往往高于顺序读数 MB 数据
- 因此，虽然读的字节少了，但**花在 seek 和调度上的时间让整体 latency 翻倍**

在高 selectivity（50%）时更惨：
- C 组 `bytes_read`（424M）与 A 组（430M）几乎相同，说明索引**几乎没有过滤掉数据**
- 但 C 组 latency（200ms）是 A 组（103ms）的 **1.94 倍**
- 这是典型的"**索引解析 + 计划生成 + 随机跳转**" overhead 未得到任何过滤收益回报

> **关键结论**：标量索引本身不是问题，"**无序数据 + 标量索引**" 的组合才是问题。聚簇的价值在于把索引查找后的数据访问从**随机 IO 转化为顺序 IO**。

### 3.4 1D 范围查询（未命中聚簇键）：零收益验证

当聚簇键是 `lat/lng`，查询过滤的是 `timestamp` 时，所有组的 speedup 都在 0.83x–1.12x 之间。这强有力地验证了：

> **聚簇的收益具有严格的维度选择性。查询必须过滤在聚簇键上才能获得收益。**

同时也说明聚簇操作本身没有引入全局性查询开销（比如破坏其他列的元数据效率）。

### 3.5 点查询：标量索引有效，聚簇无关

点查询 `lat = x AND lng = y` 中：
- 聚簇无帮助（B 组 vs A 组：0.98x）
- 纯标量索引带来 2.26x 提速（C 组）
- 所有组 `bytes_read = 0`，因为 Lance 的 min-max metadata 已能拒绝大多数 fragment

**收益来源**：BTREE 索引直接定位到目标 fragment，跳过了 metadata 逐层判定的少量开销。

### 3.6 全表扫描：聚簇带来轻微顺序读优势

全表扫描（无过滤条件）中：
- B 组比 A 组快 **1.29x**
- 读的总字节数几乎不变

**收益来源**：聚簇重排后，相关列（`lat`, `lng`）的数据在物理上更连续。列式存储的顺序扫描能更好地利用 CPU cache 和存储预读（readahead），减少了 CPU/数据搬运开销。

### 3.7 混合条件：部分聚簇键命中足够有效

查询 `lat BETWEEN ... AND category = 'A'` 的收益曲线与纯 2D Range 几乎一致：
- 0.1% selectivity：75x IO 减少
- 1.0% selectivity：49x IO 减少

**收益来源**：`lat` 的范围过滤先通过聚簇的物理局部性定位到少量候选 fragment，然后在这些 fragment 内部对 `category` 做二次过滤。只要第一步的剪枝足够强，第二步的成本就被摊薄了。非聚簇列的等值条件不会削弱聚簇的核心收益。

## 4. 向量查询：当前测试条件下的发现与局限性

### 4.1 测试条件与局限性说明

本节结论**严格限定于**以下测试条件：
- **数据规模**：Medium（1,000,000 行）
- **数据分布**：Uniform
- **向量索引**：IVF_PQ，128 partitions，16 sub-vectors
- **对照组**：A（无索引）、F（仅 IVF_PQ）、E（聚簇 + IVF_PQ）

**未覆盖的变量**：
- 仅测试了 Uniform 分布，未覆盖 Gaussian 或 Skewed 分布的向量场景
- 仅测试了 128 partitions，未测试 32/256 partitions
- `scan_stats_callback` 无法捕获 IVF_PQ 索引文件的读取 I/O，导致 `bytes_read` 和 `iops` 在 F/E 组均为 0，缺少物理层对比
- 未显式测试 `prefilter=True` 与 `prefilter=False` 的差异

因此，本节结论**不应被推广为**"聚簇在所有向量场景下都有害"。更准确的表述是：在 **1M 行 / Uniform / 128 partitions** 条件下，聚簇未显现出额外的正向收益。

### 4.2 向量索引本身是绝对主导因素

| 查询 | A 组 Latency | F 组 Latency | A→F Speedup |
|:---|---:|---:|---:|
| V1 纯向量 ANN | 128.15 ms | 14.93 ms | **8.59x** |
| V2 + 2D 过滤 0.1% | 118.38 ms | 12.67 ms | **9.34x** |
| V3 + 1D 过滤 0.1% | 140.46 ms | 10.53 ms | **13.34x** |

有无 IVF_PQ 向量索引决定了 8–13 倍的性能差异。这是向量查询性能的决定性来源。

### 4.3 聚簇在端到端 latency 中的微小负向差异

| 查询 | F 组 Latency | E 组 Latency | F→E 比例 |
|:---|---:|---:|---:|
| V1 纯向量 ANN | 14.93 ms | 18.69 ms | **0.80x** |
| V2 + 2D 过滤 0.1% | 12.67 ms | 15.78 ms | **0.80x** |
| V2 + 2D 过滤 50% | 14.80 ms | 19.34 ms | **0.77x** |
| V3 + 1D 过滤 0.1% | 10.53 ms | 13.19 ms | **0.80x** |
| V3 + 1D 过滤 50% | 13.54 ms | 19.07 ms | **0.71x** |

在全部 9 个测试点中，E 组 latency 均略高于 F 组，差异幅度在 **20–30%**（约 3–5ms）。

### 4.4 差异来源的推测

由于 `scan_stats_callback` 无法统计索引 I/O，以下分析基于 latency 数据的行为模式进行推测：

**证据 1：V1（纯 ANN，无标量过滤）也慢了 20%**
- 这说明 slowdown 不是标量过滤路径的问题
- 纯 ANN 不涉及 `lat/lng` 过滤，聚簇键完全不会被用到

**证据 2：V2（命中聚簇键）和 V3（未命中聚簇键）的 slowdown 幅度几乎相同**
- 如果聚簇的标量过滤优化在起作用，V2 应该明显优于 V3
- 但两者同步变化，说明标量过滤的收益被 IVF_PQ 搜索成本淹没

**最可能的根因**：
IVF_PQ 索引构建包含 k-means 聚类和 PQ 子向量训练。这两个过程可能对数据的物理顺序敏感：
- **无聚簇（F）**：数据保持原始生成顺序，k-means 训练时的样本流分布较均匀
- **聚簇后（E）**：数据按 `lat/lng` 重排，相同空间区域的向量在物理上连续存放

聚簇后的数据重排可能导致：
- k-means 质心分布轻微退化
- 某些 partition 过度聚集，某些 partition 稀疏
- 查询时需要访问更多 partition（effective nprobe 增加）

在 1M 行规模下，这表现为约 3–5ms 的固定 latency 增加。

### 4.5 为什么标量过滤的优化没有被观测到？

即使聚簇让标量过滤快了 10 倍（参考 Phase 2 的 50x–80x IO 减少），在向量查询中这个优化空间的绝对值很小：

| 成本项 | 估计耗时 | 说明 |
|:---|---:|:---|
| IVF_PQ 索引搜索 | 10–16 ms | **绝对主导** |
| 距离计算与排序 | 2–4 ms | 次要 |
| 标量过滤 | 1–2 ms | 在整体中占比小 |
| 聚簇带来的标量过滤优化 | ~0.5 ms | 即使快 10 倍，也只有 ~1ms 优化空间 |

1ms 的潜在优化被 3–5ms 的索引效率波动完全覆盖，因此在端到端 latency 中无法观测到正向收益。

### 4.6 产品层面的启示

| 场景 | 当前测试条件下的建议 |
|:---|:---|
| 以 ANN/向量搜索为主，标量过滤简单 | **直接建 IVF_PQ 索引（F 组模式）** |
| 混合负载（大量标量查询 + 少量向量查询） | **聚簇 + 向量索引（E 组模式）**，标量侧收益可覆盖向量侧轻微波动 |
| 超大向量数据集 + 复杂低 selectivity 预过滤 | 需更大规模/不同分布的实测验证 |

## 5. 边界条件：维度、分布与规模

### 5.1 维度：2D 最优，4D 明显稀释

在 S1（2D Range `lat/lng`）中，D 组（聚簇+索引）的收益随维度变化：

| 维度 | 聚簇键 | 0.1% IO Reduction | 10% Speedup | 原因 |
|:---|:---|---:|---:|:---|
| 1D | `timestamp` | 1.00x | 0.91x | 聚簇键不是 `lat/lng`，不生效 |
| **2D** | `lat, lng` | **79.56x** | **5.53x** | Hilbert 曲线最优匹配 |
| 3D | `lat, lng, category_id` | 30.26x | 4.85x | 加入第三维后 `lat/lng` 局部性开始稀释 |
| 4D | `lat, lng, category_id, timestamp` | 11.63x | 4.01x | 4D Hilbert 逼近误差增大，核心维度局部性显著削弱 |

**1D 时间查询（S2）的对比**：
- 1D Direct Sort 对 `timestamp` 过滤达到 **14.8x 提速**
- 4D Hilbert 重新包含 `timestamp` 后恢复至 **8.6x 提速**
- 这说明 Hilbert 曲线对尾端维度的保持能力不如 Direct Sort 对 1D 的精确

### 5.2 分布：Gaussian 是甜蜜点，Skewed 存在天然上限

S1（2D Range）D 组 0.1% selectivity 下：

| 分布 | Speedup | IO Reduction | 收益来源分析 |
|:---|---:|---:|:---|
| Uniform | 1.88x | 79.56x | 理想基准，收益稳定可预期 |
| **Gaussian** | **2.24x** | **552.10x** | 高斯聚集使数据高度压缩在少数连续 fragment 中，查询几乎可跳过 99.8% 的数据 |
| Skewed | 1.88x | 2.45x | Zipf 热点数据在原始数据中已极度分散，聚簇后热点区仍占大量读取 |

**Gaussian 的极致收益**：
- A 组读 32MB，D 组只读 **58KB**
- 真实世界的城市热点、用户活跃聚集区是聚簇收益的最优场景

**Skewed 的异常表现**：
- A 组在所有 selectivity 下都读约 525MB（metadata 几乎无法跳过任何 fragment）
- D 组在所有 selectivity 下稳定在 213MB
- S3 点查询在 A 组读了 525MB（唯一出现"点查询读全表"的情况）
- 原因是 Zipf 的热门值散布在几乎每个 fragment 中，即使聚簇后热点数据被集中，这些热点行仍需被读取

### 5.3 规模：10M 行触发 OOM

2D Uniform Large（10,000,000 行）测试在 `table.cluster()` 阶段被系统 kill（exit code 137 = SIGKILL，OOM）。

**分析**：
- 当前聚簇实现需要将排序后的数据全部加载到内存中再进行分片写入
- 10M 行 × 128 维向量 + 其他列的峰值内存需求超出了测试环境可用内存
- 这表明当前实现采用**全内存排序**，而非外部排序（external sort）

**影响**：
- 对于生产环境的大数据集，这是一个可扩展性瓶颈
- 建议在文档中明确标注聚簇的内存需求，或考虑在 Rust 核心中实现流式/外部排序

### 5.4 类型限制：Utf8 不支持聚簇

多维聚簇当前仅支持数值类型（int, float, timestamp）。3D/4D 测试最初使用 `category`（Utf8）直接报错：
```
ValueError: Invalid input, Type 'Utf8' is not supported for clustering
```

修复方案是将字符串列编码为 `category_id`（int32）。用户在实际使用中需注意此限制。

## 6. 工程实践建议

### 6.1 配置选择指南

| 工作负载特征 | 推荐配置 | 原因 |
|:---|:---|:---|
| 低 selectivity 标量范围查询（<5%） | **聚簇 + 标量索引（D 组）** | 可达 50-80 倍 IO 减少 |
| 中等 selectivity 标量查询（5%-20%） | **聚簇（B 组）或 D 组** | 顺序局部性收益最大化 |
| 高 selectivity 标量查询（>50%） | **D 组** | 仍有 2-3 倍提速 |
| 纯向量 ANN 为主 | **仅向量索引（F 组）** | 在当前测试条件下最优 |
| 混合负载（大量标量 + 少量向量） | **聚簇 + 向量索引（E 组）** | 标量侧收益覆盖向量侧波动 |
| 主要按时间过滤 | **1D Direct Sort** | 14.8x 提速，最精确 |
| 主要按空间过滤 | **2D Hilbert** | 79x IO 减少，收益峰值最高 |
| 数据呈高斯/聚集分布 | **强烈推荐聚簇** | 可达 552x IO 减少 |
| 数据呈 Zipf/极端偏斜 | 谨慎评估 | 热点数据需全读，收益上限约 2.5x |

### 6.2 给 LanceDB 产品的改进建议

1. **索引建议器应感知聚簇状态**：为未聚簇数据推荐标量索引可能导致负优化（C 组现象）。
2. **查询计划器应支持"跳过索引"启发式规则**：在高 selectivity 无序数据 + 标量索引场景下，自动回退全表扫描可能更优。
3. **监控指标应同时暴露 `bytes_read` 和 `iops`**：只看 latency 会掩盖随机 IO 问题。
4. **向量索引查询需支持索引级 I/O 统计**：当前 `scan_stats_callback` 无法捕获 IVF_PQ 索引文件读取，导致向量场景缺少物理层指标。
5. **聚簇操作需要流式/外部排序支持**：10M 行 OOM 暴露了内存扩展性瓶颈。
6. **文档需明确标注类型限制**：Utf8 不支持聚簇，用户需手动编码为整数。
