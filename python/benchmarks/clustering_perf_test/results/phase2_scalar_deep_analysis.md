# Phase 2 深度分析：多维聚簇在标量查询中的收益机理与边界条件

> **测试配置**：Medium (1,000,000 行) / Uniform 分布 / 2D 聚簇 (`lat`, `lng`) / 20 次正式测试

---

## 1. 核心现象总览

| 组别 | 本质 | 最佳表现 | 最差表现 |
|:---|:---|:---|:---|
| **A** | 无序数据，无索引 | 基准线 | 高 selectivity 时 latency 最高 |
| **B** | 纯聚簇（物理重排） | 10% selectivity 2D Range **5.6x 提速** | 0.1% selectivity 时几乎无收益 |
| **C** | 纯 BTREE 标量索引 | 点查询 **2.3x 提速** | 2D Range 查询 **负优化** |
| **D** | 聚簇 + 标量索引 | 0.1% selectivity 2D Range **79x IO 减少，1.9x 提速** | 50% selectivity 时仍有 **3x IO 减少** |

---

## 2. 为什么纯标量索引（C 组）是负优化？

### 2.1 数据：负优化的铁证

**S1 (2D Range Query)**：

| Selectivity | C 组 Latency | A 组 Latency | C 组 IOPS | A 组 IOPS |
|:---|---:|---:|---:|---:|
| 0.1% | 12.51 ms | 6.99 ms | **2,262** | **6** |
| 1.0% | 14.23 ms | 10.63 ms | 136 | 6 |
| 10.0% | 70.36 ms | 48.02 ms | 6 | 4,625 |
| 50.0% | 200.05 ms | 103.24 ms | 18,481 | 18,777 |

### 2.2 根因：无序数据 + BTREE 索引 = 随机 IO 灾难

在 Lance 的列式存储架构中，查询成本由两部分组成：
1. **数据读取成本**（`bytes_read`）
2. **IO 调度成本**（`iops`，即 seek、open page、fragment 元数据读取的次数）

C 组的数据是**原始无序写入**的。BTREE 索引虽然能根据 `lat >= ? AND lat <= ?` 快速定位匹配行，但这些行在物理存储上**散落在上百个不连续的 Fragment 中**。索引查找后，Lance 需要：
- 逐个打开 Fragment
- 读取该 Fragment 的 min-max metadata
- 再读取匹配的 Page

这导致 **IOPS 从 A 组的 6 次暴涨到 C 组的 2,262 次**（0.1% selectivity）。在现代存储（尤其是对象存储）中，一次随机 seek 的延迟可能等同于顺序读数 MB。因此虽然 C 组 `bytes_read` 减少了 5 倍（28M → 5M），但 **seek 开销完全吞噬了节省的带宽收益**。

### 2.3 高 selectivity 时的双重惩罚

在 50% selectivity 时：
- C 组 `bytes_read`（424M）与 A 组（430M）几乎相同，说明索引**几乎没有过滤掉数据**
- 但 C 组 latency（200ms）是 A 组（103ms）的 **1.94 倍**

这是因为查询引擎付出了完整的 "**索引解析 + 计划生成 + 随机跳转调度**" 成本，却得不到任何过滤收益。这种情况在数据分布均匀、selectivity 高、或过滤条件覆盖大量数据时极为常见。

### 2.4 为什么 D 组（聚簇+索引）截然不同？

对比 0.1% selectivity 下 C 组与 D 组：

| 指标 | C 组 | D 组 | 差距 |
|:---|---:|---:|---:|
| Latency | 12.51 ms | 3.72 ms | **3.4x** |
| Bytes Read | 5,196,928 | 351,984 | **14.8x** |
| IOPS | 2,262 | 84 | **26.9x** |

聚簇将 `lat` 相近的行物理上聚集在一起。BTREE 索引查到的匹配行不再散落在上千个 fragment 中，而是**集中在少量连续的 page 里**。索引的价值从 "随机跳转导航" 变成了 "快速定位到一片连续数据区，然后顺序扫描"。

> **关键结论**：标量索引本身不是问题，**"无序数据 + 标量索引" 的组合才是问题**。聚簇解决的不是索引"精度"，而是索引查找后的**数据访问模式**（从随机 IO 变为顺序 IO）。

## 3. 纯聚簇（B 组）的收益模式：顺序局部性 > 数据跳过

### 3.1 反直觉的发现

B 组在 S1 中的 `bytes_read` 减少非常有限（0.1% selectivity 仅减少 1.38x），但 latency 在某些 selectivity 下却非常出色（10% 时 5.6x 提速）。更奇怪的是：

**S5 (Mixed Condition, 10% selectivity)**：
| 指标 | A 组 | B 组 | 变化 |
|:---|---:|---:|---:|
| Latency | 95.91 ms | 20.30 ms | **4.7x 提速** |
| Bytes Read | 52,356,559 | 69,411,197 | **+32.6%** |
| IOPS | 13,002 | 2,210 | **-83%** |

B 组读了 **更多字节**，但速度快了 **近 5 倍**。这是一个极为重要的信号。

### 3.2 解释：顺序读取 vs 随机读取的 trade-off

在未聚簇的 A 组数据中，虽然过滤条件能跳过一些 fragment，但被命中的 fragment 在物理上是不连续的。查询引擎需要：
- 读取 fragment 1 的 metadata
- seek 到 fragment 50
- 读取 fragment 50 的 metadata
- seek 到 fragment 120...

这种**随机 seek 模式**导致了极高的 IOPS（13,002 次），即使最终读的总字节数"只有" 52MB，引擎也花了大量时间在 IO 调度上。

而 B 组聚簇后，`lat` 相近的数据被连续存放。过滤条件 `lat BETWEEN x AND y` 命中的是**物理上连续的一大段数据**。Lance 不需要频繁 seek，而是可以：
- 顺序读取一个连续区域
- 在这个连续区域内同时应用 `lat` 和 `category` 过滤

结果是：**虽然某些无关行也被读进来了（导致 bytes_read 上升 32%），但 IOPS 暴跌 83%，顺序带宽利用率极高，最终 latency 大幅下降。**

### 3.3 B 组在不同 selectivity 下的表现分化

| Selectivity | S1 Latency Speedup | S1 IO Reduction | 主导机制 |
|:---|---:|---:|:---|
| 0.1% | 0.98x | 1.38x | 数据跳过开始生效，但顺序读优势尚未拉开 |
| 1.0% | 1.34x | 1.39x | 局部性优势开始显现 |
| 10.0% | **5.61x** | 1.56x | **顺序局部性主导**，随机→顺序的转换收益最大 |
| 50.0% | 3.50x | 2.71x | 跳过+局部性双重收益 |

为什么 10% selectivity 是 B 组的"甜蜜点"？
- **0.1% 时**：A 组本身就能跳过绝大多数 fragment（metadata 判定不匹配），所以 A 组 latency 已经很短（7ms）。B 组再优化空间有限。
- **10% 时**：A 组需要打开大量分散的 fragment（IOPS 高），但每个 fragment 只读一小部分。B 组把这些 fragment"压缩"成连续的几个大块，顺序一扫而过，收益最大化。
- **50% 时**：大部分 fragment 本来就需要读，A 组的随机 seek 惩罚减小，所以 B 组的相对收益有所下降。

> **关键结论**：纯聚簇的核心收益机制在 Medium 规模下**不是 fragment 跳过**，而是**将随机 IO 转换为顺序 IO**。这在 5%-20% selectivity 区间收益最显著。

---

## 4. D 组（聚簇+索引）的协同效应：两种机制叠加

D 组同时享受了：
1. **聚簇带来的顺序局部性**（减少 IOPS）
2. **BTREE 索引带来的精准定位**（减少 bytes_read）

### 4.1 S1 中的 D 组表现

| Selectivity | D 组 Latency | D 组 Bytes Read | D 组 IOPS | 机制拆解 |
|:---|---:|---:|---:|:---|
| 0.1% | 3.72 ms | 351,984 | 84 | 索引精准定位到一小块连续区域，顺序读取 |
| 1.0% | 5.01 ms | 557,416 | 68 | 同上，定位区域稍大 |
| 10.0% | 8.68 ms | 7,013,297 | 92 | 索引过滤掉部分区域，聚簇保证命中区域连续 |
| 50.0% | 41.82 ms | 144,900,355 | 344 | 索引过滤效果减弱，但仍比 A/B 高效 |

对比 S1 10% selectivity：
- A 组：48 ms，38.6M bytes，4,625 IOPS
- B 组：8.6 ms，24.7M bytes，107 IOPS
- D 组：8.7 ms，7.0M bytes，92 IOPS

D 组和 B 组 latency 几乎相同，但 **D 组读了少 3.5 倍的数据**。这说明在 10% selectivity 下，latency 瓶颈已经是 "顺序读带宽" 而非 "IO 调度"，所以进一步减少 bytes_read 对 latency 帮助有限。但在**对象存储或高并发场景**下，7M vs 24M 的带宽差异会显著放大。

> **关键结论**：D 组是"最优解"，不仅 latency 快，而且** bytes_read 极低**。这意味着在按流量计费的存储环境（如云对象存储）中，D 组能显著降低查询成本。

---

## 5. S2（1D Timestamp Range）：聚簇键未命中 = 零收益

S2 过滤的是 `timestamp`，而聚簇键是 `lat/lng`。四个组在所有 selectivity 下的表现都高度一致：

| Selectivity | 最佳 Speedup | 最佳 IO Reduction |
|:---|---:|---:|
| 0.1% | 1.01x | 1.00x |
| 1.0% | 1.06x | 1.00x |
| 10.0% | 1.00x | 1.00x |
| 50.0% | 1.12x | 1.00x |

这强有力地验证了：
> **多维聚簇的收益具有维度选择性。查询必须过滤在聚簇键上才能获得收益。**

同时也说明聚簇操作本身**没有引入全局性的查询开销**（比如破坏其他列的元数据效率）。

---

## 6. S3（Point Query）：标量索引有效，聚簇无关

| 组别 | Latency | Speedup | Bytes Read | IOPS |
|:---|---:|---:|---:|---:|
| A | 6.43 ms | 1.00x | 0 | 0 |
| B | 6.60 ms | 0.98x | 0 | 0 |
| C | 2.85 ms | 2.26x | 0 | 0 |
| D | 2.98 ms | 2.16x | 0 | 0 |

所有组的 `bytes_read = 0`，因为 Lance 的 min-max metadata 本身就足以拒绝大多数 fragment，无需读取数据页。聚簇对 point query 没有帮助，因为：
- metadata 过滤已经做得很好
- 真正需要读的数据量极小（可能只命中 0-1 个 fragment）
- 2.2x 提速完全来自 BTREE 索引直接定位到目标 fragment，跳过了 metadata 逐层判定

> **关键结论**：点查询场景下，聚簇无额外收益，标量索引是唯一的优化手段。

---

## 7. S4（Full Scan）：聚簇带来意外之喜

| 组别 | Latency | Speedup | Bytes Read | IOPS |
|:---|---:|---:|---:|---:|
| A | 84.30 ms | 1.00x | 559,893,022 | 43 |
| B | 65.31 ms | 1.29x | 559,971,530 | 540 |

聚簇后的全表扫描快了 **29%**，而读的总字节数几乎不变。原因是：
- 聚簇重排后，相关列（`lat`, `lng`）的数据在物理上更连续
- 列式存储的顺序扫描能更好地利用 CPU cache 和预读（readahead）
- 虽然 B 组 IOPS 更高（540 vs 43），但这反映了 Lance 以更大粒度顺序读取 fragment，减少了小粒度随机调度

> **关键结论**：聚簇不会损害全表扫描，反而能通过更好的物理局部性带来轻微性能提升。这意味着用户无需担心 "为某些查询做聚簇会拖慢其他查询"。

---

## 8. S5（Mixed Condition）：部分聚簇键命中足够有效

S5 的查询是 `lat BETWEEN ... AND category = 'A'`。

D 组表现：
| Selectivity | Latency | Speedup | IO Reduction |
|:---|---:|---:|---:|
| 0.1% | 4.76 ms | 2.52x | 75.39x |
| 1.0% | 7.54 ms | 3.51x | 48.98x |
| 10.0% | 21.17 ms | 4.53x | 7.15x |
| 50.0% | 78.63 ms | 2.38x | 1.14x |

与 S1（纯 `lat/lng` 2D Range）几乎完全一致的曲线。这说明：
> **在多维聚簇键中，只要有一个维度（这里是 `lat`）的范围过滤足够 selective，非聚簇列的等值条件（`category = 'A'`）不会削弱聚簇的收益。**

查询引擎的执行逻辑是：
1. 利用 `lat` 的范围先通过聚簇的物理局部性/索引定位到少量候选 fragment
2. 在这些候选 fragment 内部，再通过 `category = 'A'` 做二次过滤

只要第一步的剪枝足够强，第二步的成本就被摊薄了。

## 9. 收益边界与适用场景总结

### 9.1 Selectivity 曲线

基于 S1 和 S5 的 D 组数据：

| Selectivity | Speedup | IO Reduction | 推荐度 |
|:---|---:|---:|:---|
| 0.1% | 1.9x–2.5x | 50x–80x | ⭐⭐⭐⭐⭐ 极高 |
| 1.0% | 2.1x–3.5x | 48x–50x | ⭐⭐⭐⭐⭐ 极高 |
| 10.0% | 4.5x–5.5x | 5x–7x | ⭐⭐⭐⭐ 高 |
| 50.0% | 2.4x–2.5x | 1.1x–3x | ⭐⭐⭐ 中等 |

注意一个反直觉的点：**latency speedup 的峰值不在最低 selectivity，而是在 10% 左右**。这是因为：
- 0.1% 时 A 组本身就已经很快（metadata 过滤效果好），优化空间被压缩
- 10% 时 A 组遭受最严重的 "命中 fragment 多且分散" 的随机 IO 惩罚，D 组的顺序局部性优势被最大化放大

### 9.2 什么场景应该用聚簇？

| 场景 | 是否推荐 | 最佳组别 |
|:---|:---|:---|
| 低 selectivity 范围查询（<5%） | **强烈推荐** | D（聚簇+索引） |
| 中等 selectivity 范围查询（5%-30%） | **强烈推荐** | B 或 D |
| 高 selectivity 范围查询（>50%） | 有一定收益 | D |
| 点查询 / 主键查找 | 不推荐 | C（纯索引） |
| 全表扫描 / 聚合 | 安全可用 | B 或 D |
| 过滤条件不在聚簇键上 | **无效** | A |
| 成本敏感（按流量计费的存储） | **强烈推荐** | D |

## 10. 工程实践建议

### 10.1 对用户的操作建议

1. **不要单独建立标量索引**：在 2D 范围查询场景下，单独的 BTREE 标量索引（C 组模式）是负优化。如果已经建了索引，考虑先聚簇再保留索引（升级为 D 组模式）。

2. **聚簇键的选择要匹配查询模式**：如果业务查询主要按 `lat/lng` 过滤，就把 `lat/lng` 设为聚簇键。如果主要按 `timestamp` 过滤，就要用 1D 聚簇或把 `timestamp` 纳入多维聚簇键。

3. **中等 selectivity 是聚簇的最大收益区**：10% 左右的 selectivity 比 0.1% 更能体现聚簇的价值。如果你的查询大多落在这个区间，聚簇的投资回报率最高。

4. **在云存储/对象存储环境中优先使用 D 组模式**：D 组的 `bytes_read` 可以比 A 组低 50-80 倍，这直接转化为云存储请求费用和出口带宽成本的下降。

### 10.2 对 LanceDB 产品的启示

1. **自动索引建议系统应感知聚簇状态**：当前测试表明，"为未聚簇数据推荐标量索引"可能会让用户获得负收益。索引建议器应该优先推荐聚簇，或在聚簇完成后再建议索引。

2. **查询计划器可考虑 "跳过索引" 的启发式规则**：对于高 selectivity 的无序数据范围查询，查询计划器如果检测到索引使用后 IOPS 会暴涨，应能自动回退到全表扫描。

3. **监控指标应同时暴露 bytes_read 和 iops**：只看 latency 或只看 bytes_read 都会误导优化决策。IOPS 是揭示随机 IO 问题的关键信号。

## 11. 待 Phase 3/4 验证的假设

1. **向量 + 标量过滤（V2/V3）**：在 ANN 查询中加上 `lat/lng` 预过滤，E 组是否能复现 D 组在标量查询中的收益？预期 E 组的 `bytes_read` 显著低于 A+E。
2. **不同分布（Gaussian vs Skewed）**：Uniform 分布下聚簇收益是否是最优情况？真实世界的聚集分布和热点分布是否会让 B 组的 "顺序局部性" 优势更加突出？
3. **不同维度（1D/3D/4D）**：1D Direct Sort 在 S2（timestamp 查询）上是否比 2D Hilbert 更高效？3D/4D 聚簇是否会因为 Hilbert 曲线逼近误差导致收益稀释？
