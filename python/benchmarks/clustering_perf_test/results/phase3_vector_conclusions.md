# Phase 3 向量融合查询测试结论与反思

> **测试配置**：Medium (1,000,000 行) / Uniform 分布 / 2D 聚簇 (`lat`, `lng`)
> **对照组**：A（无聚簇、无向量索引）/ E（聚簇 + IVF_PQ 向量索引）
> **测试查询**：V1（纯向量 ANN）、V2（向量 + 2D 标量预过滤）、V3（向量 + 1D 时间预过滤）

## 2. 关键发现：E 组的 `bytes_read = 0` 意味着什么？

在所有向量查询中，E 组的 `bytes_read_avg` 和 `iops_avg` 均为 **0**。这不是因为真的没有 I/O，而是因为：

1. **IVF_PQ 向量索引查询走了独立的索引路径**，`ds.scanner(nearest=...)` 在执行时优先从索引文件中获取候选向量，而不是扫描底层数据文件。
2. `scan_stats_callback` 当前只统计**底层数据扫描器**的 I/O，**不统计索引读取 I/O**。
3. 因此，E 组 512MB 的向量数据实际上被索引"绕过"了，`bytes_read` 只反映了是否回表读取原始数据列。

这带来了一个严重的测量盲区：
> **我们无法通过 `scan_stats_callback` 比较 A 组和 E 组的物理 I/O 差异。** E 组的 0 bytes_read 不等于"零成本"，而是意味着统计口径没有覆盖到索引 I/O。

A 组之所以显示 512MB，是因为它**没有向量索引**，查询引擎必须暴力扫描整个 `embedding` 列（以及可能的标量过滤列），所以每次查询都要读约 512MB。

## 3. 最大的设计缺陷：Speedup 主要来自向量索引，而非聚簇

这是 Phase 3 最值得反思的结论。

当前对照组设计是：
- **A 组**：无聚簇、**无向量索引**
- **E 组**：聚簇、**有 IVF_PQ 向量索引**

因此，测出的 5x–10x speedup **绝大部分来自"有向量索引 vs 无向量索引"**，而不是"聚簇 vs 未聚簇"。

### 3.1 证据 1：V1（纯向量 ANN）就有 9.13x 提速

按照原始设计，V1 的预期是 "验证纯向量查询无收益（对照）"。但实际结果是 **E 组比 A 组快 9.13x**。

这完全不可能是聚簇带来的——纯 ANN 查询的 top-k 检索路径根本不涉及标量过滤，聚簇键 `lat/lng` 完全不会被使用。9.13x 的提速纯粹是因为 **A 组在做暴力搜索，E 组在用 IVF_PQ 索引**。

### 3.2 证据 2：V3（向量 + 1D 时间过滤）同样有 5.7x–9.7x 提速

我们在 Phase 2 中已经验证：**2D 聚簇对 `timestamp` 过滤没有任何收益**（S2 的 speedup 在 0.83x–1.12x 之间）。

但 Phase 3 的 V3 中，E 组仍然比 A 组快了 5.7x–9.7x。如果聚簇对 timestamp 过滤没有帮助，那这部分 speedup 只能来自向量索引本身。

### 3.3 证据 3：E 组在 V2/V3 中的 latency 对 selectivity 不敏感

| Selectivity | V2 E 组 | V3 E 组 |
|:---|---:|---:|
| 0.1% | 13.71 ms | 12.73 ms |
| 1.0% | 13.38 ms | 14.14 ms |
| 10.0% | 13.34 ms | 15.17 ms |
| 50.0% | 17.20 ms | 19.93 ms |

如果聚簇的标量过滤在 V2/V3 中起到了显著的数据跳过作用，我们预期：
- V2（命中聚簇键 `lat/lng`）在低 selectivity 时应该比 V3（未命中聚簇键 `timestamp`）快得多
- 随着 selectivity 上升，V2 的 E 组 latency 应该显著增加（因为需要读更多数据）

但实际数据：
- V2 和 V3 的 E 组 latency 几乎相同（12–17ms）
- 从 0.1% 到 50%，latency 仅增加了 3–7ms

这说明**标量过滤的成本在整体向量索引查询中被完全淹没**。IVF_PQ 索引的 nprobe、候选向量计算、距离排序才是主导成本。

## 4. 当前测试能告诉我们什么？

虽然无法隔离聚簇的独立贡献，但仍有几个有价值的发现：

### 4.1 端到端体验：聚簇 + 向量索引的组合模式非常强大

对于用户来说，"E 组"是一个完整的推荐配置（先聚簇，再建向量索引）。从端到端 latency 看：
- 纯向量搜索：18 ms
- 向量 + 2D 过滤：13–17 ms
- 向量 + 1D 过滤：13–20 ms

对比 A 组（无索引）的 110–166 ms，**E 组模式将向量查询的响应时间稳定控制在 20ms 以内**。这是一个明确的工程收益。

### 4.2 标量过滤对 ANN 查询的影响：在 IVF_PQ 路径中相对可控

V2/V3 中，即使在 50% selectivity 下，E 组的 latency 也仅从 ~13ms 上升到 ~20ms。这说明：
- Lance 的预过滤（prefilter）实现效率较高
- 在 medium 规模（1M 行）下，高 selectivity 的标量过滤不会让向量索引查询失控

### 4.3 E 组的 `bytes_read = 0` 揭示了一个产品特性

向量索引查询一旦命中 IVF_PQ 索引，就**不需要回表读取原始 embedding 列**。这意味着：
- 频繁执行的 ANN 查询，其主要的存储 I/O 成本被转移到了索引文件上
- 原始数据文件在 ANN 查询路径中几乎不会被扫描（除非使用 `refine` 或需要读取其他列）

## 5. Phase 3 的局限性与修正建议

### 5.1 核心局限：缺少 "有向量索引但未聚簇" 的对照组

要真正测量"聚簇对向量+标量查询的贡献"，必须引入一个新的对照组：

| 组别 | 数据状态 | 用途 |
|:---|:---|:---|
| **A'** | 无聚簇 + **有 IVF_PQ 向量索引** | 向量索引基准线 |
| **E** | 聚簇 + 有 IVF_PQ 向量索引 | 测量聚簇的额外贡献 |

只有比较 A' 和 E，才能回答：**在已经有向量索引的前提下，聚簇还能为带标量过滤的向量查询带来多少额外收益？**

根据 Phase 2 的标量查询经验，我们的假设是：
- V2（2D 过滤，命中聚簇键）：A' vs E 可能有 2–5x 的额外提速
- V3（1D 过滤，未命中聚簇键）：A' vs E 的收益应接近 1x

### 5.2 修正方案

如果希望在后续阶段补全这个对照，可以：
1. 新增一个临时脚本，创建 `group_a_prime`（无聚簇 + IVF_PQ，128 partitions）
2. 只跑 V2/V3 两个查询场景，与已有的 E 组数据对比
3. 或在 Phase 4 的边界条件测试中，将 A' 作为固定对照组纳入

---

## 6. Phase 3 结论

1. **当前 Phase 3 测出的 5x–10x speedup 主要来自 IVF_PQ 向量索引本身，而非聚簇**。这是由对照组设计缺陷导致的——A 组没有向量索引，无法作为公平的聚簇对照。
2. **聚簇 + 向量索引（E 组）的端到端 latency 表现优异**：所有向量查询稳定在 13–20ms，显著优于无索引的暴力搜索（110–166ms）。
3. **在 IVF_PQ 路径中，标量过滤的成本对 selectivity 相对不敏感**。即使 50% selectivity， latency 增幅也很小（+3–7ms）。
4. **`scan_stats_callback` 无法捕获向量索引 I/O**，导致 `bytes_read` 和 `iops` 在 E 组全部为 0。向量场景的物理层指标需要依赖其他工具（如 `strace`、磁盘监控）才能准确测量。
5. **下一步建议**：引入 A' 组（无聚簇 + 向量索引）作为真正的聚簇对照，才能量化聚簇在向量-标量融合查询中的独立贡献。

---

## 7. 与 Phase 2 的关联

Phase 2 已经证明：**聚簇在低 selectivity 标量查询中能带来 50–80 倍的 IO 减少**。如果这个效应能传递到向量查询的预过滤阶段，那么在"有向量索引"的基准上，聚簇应该还能再带来额外的标量过滤优化。

但由于当前测试设计无法隔离这一层，Phase 3 的结论是**工程推荐性的**（"E 组模式很好"），但**不是归因性的**（"聚簇本身贡献了多少"）。
