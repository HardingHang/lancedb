# Phase 3 隔离分析：聚簇在向量查询中的真实贡献

> **关键改进**：引入 F 组（Vector Index Only，无聚簇），与 A 组（无索引）和 E 组（聚簇+向量索引）形成完整对照链。
> **测试配置**：Medium (1,000,000 行) / Uniform 分布 / 2D 聚簇 / 128 partitions IVF_PQ

---

## 1. 三层对照结果

| 查询 | Selectivity | A (无索引) | F (仅向量索引) | E (聚簇+向量索引) | A→F Speedup | F→E Ratio |
|:---|:---|---:|---:|---:|---:|---:|
| **V1** Pure Vector | none | 128.15 ms | 14.93 ms | 18.69 ms | **8.59x** | **0.80x** |
| **V2** Vector + 2D Filter | 0.1% | 118.38 ms | 12.67 ms | 15.78 ms | **9.34x** | **0.80x** |
| **V2** Vector + 2D Filter | 1.0% | 126.20 ms | 11.81 ms | 15.99 ms | **10.68x** | **0.74x** |
| **V2** Vector + 2D Filter | 10.0% | 121.66 ms | 11.82 ms | 14.47 ms | **10.29x** | **0.82x** |
| **V2** Vector + 2D Filter | 50.0% | 114.68 ms | 14.80 ms | 19.34 ms | **7.75x** | **0.77x** |
| **V3** Vector + 1D Filter | 0.1% | 140.46 ms | 10.53 ms | 13.19 ms | **13.34x** | **0.80x** |

---

## 2. 核心发现 1：向量索引是绝对主导因素（A→F = 8-13x）

F 组（无聚簇，仅 IVF_PQ）在所有场景下都比 A 组（暴力搜索）快了 **8 到 13 倍**。这是向量查询性能的决定性来源。

无论是否加上标量过滤、无论标量过滤是否命中聚簇键，IVF_PQ 索引都将查询从"全表向量扫描"转换为"索引分区扫描"，这是数量级的提升。

---

## 3. 核心发现 2：聚簇在向量查询中不仅没有额外加速，反而慢了 20-30%（F→E = 0.71-0.82x）

这是**与原始假设完全相反**的结果。在所有 9 个测试点中，E 组（聚簇+向量索引）**无一例外地慢于** F 组（仅向量索引）。

### 3.1 为什么聚簇后向量查询反而变慢？

**关键证据链：**

1. **V1（纯 ANN，无标量过滤）也慢了 20%**：F 14.9ms → E 18.7ms
   - 这说明 slowdown **不是标量过滤路径的问题**
   - 纯 ANN 根本不涉及 `lat/lng` 过滤，聚簇键完全不会被读取

2. **V2（命中聚簇键）和 V3（未命中聚簇键）的 slowdown 幅度几乎相同**
   - V2 0.1%：0.80x | V3 0.1%：0.80x
   - V2 50%：0.77x | V3 50%：0.71x
   - 如果聚簇的标量过滤优化在起任何作用，V2 应该明显优于 V3。但两者同步变化。

3. **所有场景的 slowdown 幅度稳定**
   - F→E 的比例在 0.71x 到 0.86x 之间波动，没有异常离群点
   - 说明这不是测试噪声，而是**系统性现象**

### 3.2 最可能的根因：聚簇重排改变了 IVF_PQ 索引的效率

IVF_PQ 索引构建包含两个训练阶段：
1. **k-means 聚类**：将向量空间划分为 `num_partitions` 个 partition
2. **PQ（Product Quantization）子向量训练**：对每个 partition 内的向量做压缩编码

这两个训练过程都可能对**数据的物理顺序和分布敏感**：

| 因素 | 无聚簇 (F) | 聚簇后 (E) | 可能影响 |
|:---|:---|:---|:---|
| 数据写入顺序 | 原始生成顺序（随机） | 按 `lat/lng` 重排 | k-means 流式训练的质心收敛不同 |
| Fragment 结构 | 默认写入产生的小 fragment | `target_rows=50K` 产生的 20 个较大 fragment | IVF 分区与 fragment 对齐方式改变 |
| 向量局部性 | 无地理相关性 | 相近地理位置的向量连续存放 | 某些 partition 可能出现向量过度聚集或稀疏 |

**核心假设**：聚簇后的数据重排导致 IVF 的 k-means 质心分布发生了轻微退化，使得查询时需要访问更多 partition（更高的 effective nprobe），从而增加了 3-5ms 的固定开销。

### 3.3 为什么标量过滤的优化没有被观察到？

即使聚簇确实让标量过滤更快了（参考 Phase 2 的 50x IO 减少），这个收益在向量查询的整体 latency 中被完全淹没了：

| 成本项 | 估计耗时 | 说明 |
|:---|---:|:---|
| IVF_PQ 索引搜索 | 10-16 ms | **绝对主导** |
| 距离计算与排序 | 2-4 ms | 次要 |
| 标量过滤（post-filter） | 1-2 ms | 被 IVF 搜索覆盖 |
| 聚簇带来的标量过滤优化 | ~0.5 ms | 即使快 10 倍，也只有 1ms 优化空间 |

在 Medium 规模（1M 行）下，标量过滤本身就不是瓶颈。因此即使聚簇将它从 1ms 优化到 0.1ms，整体 latency 从 15ms 降到 14ms 的变化也几乎不可观测——反而被 IVF_PQ 索引效率的 3-5ms 波动完全覆盖。

---

## 4. 这个结果否定了聚簇的向量查询价值吗？

**没有完全否定，但揭示了重要的边界条件：**

### 4.1 当前规模下（1M 行），聚簇对向量查询的端到端收益为负

在 `medium` 规模、`128 partitions`、Uniform 分布的条件下：
- **直接建 IVF_PQ 索引（F 组）** 是向量查询的最优配置
- **先聚簇再建索引（E 组）** 会让向量查询慢 20-30%

### 4.2 但这不意味着聚簇在所有向量场景下都是有害的

有几个可能改变结论的变量：

1. **更大规模（Large = 10M 行）**：
   - 如果标量过滤成本从 1ms 上升到 10-20ms，聚簇的 10x 优化就可能产生 9-18ms 的整体 latency 改善
   - 这可能足以抵消或超过 IVF_PQ 的 3-5ms 效率损失

2. **更高的 selectivity 或更复杂的标量过滤**：
   - 如果预过滤需要从数十万个候选向量中筛选，聚簇的数据跳过优势可能被放大

3. **不同的 IVF_PQ partition 数**：
   - 256 partitions 可能比 128 partitions 对数据顺序更不敏感
   - 或者更小的 partitions 能让标量过滤在 partition 级别提前剪枝（如果 Lance 的查询计划支持）

4. **Prefilter 模式（如果底层使用了 prefilter）**：
   - 当前测试默认走的是 `prefilter=False`（post-filter）还是 `prefilter=True`？
   - 如果是 post-filter，标量过滤只在 IVF 召回后才执行，聚簇的优势根本无法体现
   - 如果是 prefilter，且 selectivity 极低，聚簇优化可能被激活

### 4.3 产品层面的启示

| 场景 | 建议配置 |
|:---|:---|
| 以 ANN/向量搜索为主，标量过滤简单 | **直接建 IVF_PQ 索引（F 组模式）**，跳过聚簇 |
| 标量过滤复杂、selectivity 极低、数据量大 | 尝试 **聚簇 + 向量索引（E 组模式）**，但需实测验证 |
| 混合工作负载（大量标量查询 + 少量向量查询） | **聚簇 + 向量索引（E 组模式）**，因为标量查询收益足以覆盖向量侧的轻微损失 |

## 5. 测量盲区的再次确认

所有 F 组和 E 组的 `bytes_read_avg = 0`，`iops_avg = 0`。

这确认了一个重要事实：
> `scan_stats_callback` 只统计**底层数据文件扫描器**的 I/O，**不统计 IVF_PQ 索引文件读取**。

因此，我们无法通过当前工具测量：
- F 组和 E 组在索引 I/O 上的真实差异
- 聚簇是否减少了 IVF 查询需要访问的 partition 数量

要深入诊断 IVF_PQ 效率退化的根因，需要在 Rust 侧增加索引级别的 tracing 或 profiling（如 k-means 质心分布统计、nprobe 命中 partition 数等）。

## 6. 与 Phase 2 的对比与统一

| 查询类型 | 聚簇收益 | 标量索引收益 | 最佳组合 |
|:---|:---|:---|:---|
| **标量 2D Range (S1)** | 显著（B 组 3-5x） | 负优化（C 组 0.5-0.7x） | **D 组（聚簇+索引）50-80x IO 减少** |
| **纯向量 ANN (V1)** | 轻微负优化（E 0.8x F） | 决定性（F 8.6x A） | **F 组（仅向量索引）** |
| **向量+2D 过滤 (V2)** | 轻微负优化（E 0.74-0.82x F） | 决定性（F 7.8-10.7x A） | **F 组（仅向量索引）** |
| **向量+1D 过滤 (V3)** | 轻微负优化（E 0.71-0.80x F） | 决定性（F 9.1-13.3x A） | **F 组（仅向量索引）** |

**统一结论**：
- 在 **1M 行 / Uniform / 128 partitions** 条件下，聚簇的价值**高度集中在标量查询**。
- 对于**向量查询，IVF_PQ 索引本身是绝对瓶颈**，聚簇带来的任何标量过滤优化都被淹没。
- 更令人意外的是，聚簇后的数据重排可能轻微**降低 IVF_PQ 的索引效率**，导致端到端 latency 小幅增加。

## 7. 下一步建议

1. **Phase 4 中测试 Large 规模（10M 行）的 V2**：验证当标量过滤成本放大后，聚簇是否能展现出正向收益。
2. **测试 prefilter=True 模式**：如果 Lance 的 `scanner(nearest=..., filter=..., prefilter=True)` 支持显式开启预过滤，观察 V2/V3 中 F vs E 的差异是否改变。
3. **尝试不同 partition 数**：测试 256 partitions 和 32 partitions 下，聚簇对 IVF_PQ 效率的敏感度。
4. **Rust 侧 profiling**：如果上述测试仍显示 E 组慢于 F 组，需要在 `lance-index` 的 IVF 路径上加 tracing，测量实际 nprobe 命中数和 partition 扫描开销。
